# Explanation and Architecture Documentation

Explain why the system is shaped as it is, what alternatives were considered, how components interact, and which constraints or assumptions drive the design. Use a context diagram, sequence, flow, or table only when it makes a non-obvious relationship clearer.

Separate current state, target state, and proposal. Label inference and unresolved decisions. Define component ownership, trust boundaries, data flows, failure domains, operational responsibilities, and decision links. Keep implementation commands in linked how-to or runbook documents.

For architecture narratives, include scope, requirements, constraints, quality attributes, alternatives, chosen approach, consequences, risks, and revisit triggers. Do not treat a diagram or written proposal as proof of deployed state.
